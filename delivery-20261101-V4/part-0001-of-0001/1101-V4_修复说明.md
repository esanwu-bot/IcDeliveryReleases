## 一、这版最重要的结构性变化：证据上车

1101 被判「不能视为重新核验」，根因不是数据错，是**包内没有原件**：
复核方只能相信 `pdf_sha256_recorded`，无法独立重算、无法逐行对照。

V2 起每个型号目录内附原厂 PDF，manifest 给出三个字段：

| 字段 | 含义 |
|---|---|
| `pdf_included` | 是否随包（本版五件全为 `true`） |
| `pdf_sha256_recorded` | 源 JSON 解析时记录的哈希 |
| `pdf_sha256_packaged` | 包内 PDF 实测哈希（原始字节） |
| `pdf_hash_match` | 两者是否一致；`false` 直接 `gate=BLOCKED` |

PDF 是二进制，按原始字节哈希；文本物料仍按 `sha256(CRLF→LF)`。
两者混用会让「复制后哈希不一致」——其实两边都没错，只是算法不同（本版踩过）。

## 二、发布状态阶梯（新增 `release_state`）

`gate` 只说「有没有硬伤」，`release_state` 说「走到哪一级」。五级只进不退：

| 状态 | 判据 | 自动 |
|---|---|---|
| `PACKAGING_PASSED` | 四件必带物料齐备 + PDF 哈希一致 | 是 |
| `DATA_VALIDATED` | `core_validation=pass` 且事实验收表无 MISMATCH | 是 |
| `IDENTITY_APPROVED` | `identity_state` ∈ {IDENTITY_SUPPORTED, BOARD_CONFIRMED} | 是 |
| `CONTENT_APPROVED` | 人工审核页面与多语言 | **否** |
| `RELEASE_APPROVED` | 人工签核放行 | **否** |

后两级只读 `signoff.json`，代码不代签。本包最高到 `IDENTITY_APPROVED`。

## 三、身份状态升为硬门禁

1101 的 `ADS8568EVM-PDK` 带着 `identity_state=IDENTITY_REVIEW` 落了 `CLEAN`，
复审判为「`CLEAN` 被误读成身份已通过」。根因是 `_gate()` 根本没读身份字段。

现在 `IDENTITY_REVIEW` 一律判 `UNRESOLVED`，理由写 `identity_state=IDENTITY_REVIEW`。
本版该件已从 `CLEAN` 变为 `UNRESOLVED`。

README 同时补了四态语义表，明确 `PATCHED` / `CLEAN` **都不代表参数正确**。

## 四、AC 性能确定性抽取（补齐 SNR / SFDR / NSD / IMD3）

此前页面上这四个符号出现 **0 次**。

为什么不能用 `find_tables().extract()`：这张表的单元格文本会串行 ——
实测 TYP 列 12 个值被并成一格（`50 535|.|539|.|548|.`），
条件列读成 `M 0xa Fx Fim FFum Afu INll - =s c –a 2le v d`（乱序）。

做法是**几何用表格、文本用词**：

1. 列带 = 所有单元格 x 边界的排序并集（本表 9 条边界 = 8 列）。
   用「单元格 (x0,x1) 对」当列会裂出 11 个假列，值全塞进一格。
2. 值按视觉行取（同一 y 带的词），一个视觉行 = 一条测试条件。
3. 符号 / 分组 / 单位这类纵向合并的标签，按单元格纵向传播。
4. 只有「单元格文本是单个数值」才按合并跨度传播 —— TYP 列被 find_tables
   判成一整格却堆了 12 个值，那不是语义合并，按单值传播会把 12 行写成同一个数。

结果：**82 行**（SNR 24 / SFDR 23 / NSD 7 / IMD3 28），覆盖双通道与单通道两种模式，
每条都带 `fIN` / `AIN` / 模式等测试条件。逐条与 p14 原文核对一致。

页面新增「AC performance」子表，表头 `SYMBOL / 条件 / MIN / TYP / MAX / UNIT`
（MIN 等记号不翻译，与读者手上的 datasheet 对得上）。

`ACCEPTANCE_SPECS` 只登记「每个符号至少几条 + 必须带条件 + 必须有单位」，
**不登记具体数值** —— 数值锁进验收表，换一版手册就会全线误报。

## 十三、V4：AC 表列角色与 amax 列角色（元宝 7.5 分复审 / V9 施工单）

### 13.1 AC 表：48 行伪造 MIN/MAX + 18 行重复（P0）

**指控成立，已独立复现**：`Counter({'mintypmax': 48, 'typ': 31, 'mintyp': 3})`。

根因不是模型，是**切行方式**：

| 失败做法 | 后果 |
|---|---|
| 按文本 y 聚类切行 | 条件列是合并单元格、内含多行文本（`AIN = –1 dBFS` / `AIN = –3 dBFS` / `fIN = 2397 MHz`），一条逻辑行被拆成 3~4 条，叠上「单值纵向传播」→ 4 条完全相同的记录（**18 条重复**） |
| 拿值区单元格当行锚点 | p14 下半段网格线缺失，`find_tables` 没切出值单元格，整块 SNR 行凭空消失（实测少 30 行） |

现行做法：**行 = 所有单元格 y 边界的排序并集**的相邻对（与切列同一路数）。
网格线就是单元格的边，并集恰好给出真实行线，相邻对不重叠。

结果：**82 行 → 64 行，指纹唯一 64 / 内容唯一 64 / 重复 0**，
与复审方独立算出的「64 个唯一组合」完全吻合。页分布
`{p14: 12, p15: 10, p16: 10, p17: 12, p18: 10, p19: 10}`，
形状分布 `T=61 / LT=3` —— **零 `mintypmax`**。

两处「整格读」的判据（都踩过）：

* **参数列必须整格读**。同一参数跨两行时 TI 把它纵向合并成一格，格里有 2 行
  文本；按行带取词只取到落在这条带里的半句（p14 NSD 读成
  `Noise spectral density, excludes fixed interleaving`，SNR 读成 `… HD2 to`）。
  纵向合并 = 该参数适用于整段跨度，整格读才对。
* **条件列不能整格读**。合并条件格跨 4 行时整格读会把 4 条子条件塞进每一行，
  正是那 18 条重复的成因。
* **分组列（f1/f2）在合并跨行时整格读**，否则 `f2 = 2403 MHz` 整段丢
  （p16/p19 的 IMD3 中间那行读成 `f1 = 2393 MHz,; AIN = –9 dBFS per tone`）。

**闸门**：新增 `check_ac_integrity()`，进 `check_core()`，四条判据 —

1. `MIN == TYP == MAX` → 判失败（疑似把 TYP 横向复制进 MIN/MAX）；
2. `MIN == MAX` 且无 `value_shape` 佐证 → 判失败；
3. `value_shape` 与实填列不符 → 判失败（有人事后改过列）；
4. `row_sha256` 撞车 → 判失败（同一原始行抽了两遍）。

拿旧 82 行数据喂进去：**96 条错误**；新 64 行：**0 条**。

### 13.2 amax：15 条列角色回验（P1，遗留老账）

1. **参数名匹配**：JSON 名里的大写编号词（`VA19` / `TMSTP` / `DA[7:0]`）与

   平局取条件最短的那条（`VA11(2)` 比 `Voltage between VD11 and VA11` 更像本行）。
2. **数值匹配**：名字对不上时（`Peak Total Input Current` 这种纯自然语言名）
   退回按 (MIN, MAX, 单位) 全等匹配，唯一命中才认。

**实测 15 checked / 15 upgraded / 0 unmatched**，全部 `column_roles_verified` +
`audited_deterministic`，带 `bbox` 与 `row_sha256`。

单值行（`Tj = 150`、`PMAX = 26.25`、`IMAX(ALL) = 100`）**只填 MAX**，
绝不复制进 MIN；展示值剥掉脚注标号（`VD11 + 0.5(5)` → `VD11 + 0.5`），
原文留在 `source.quote`。
