V5 的三件 P1（韩语清零、面包屑、板卡三桶）已被复审确认修好；本版只处理**新暴露的两类问题**：

## 一、自证链闭环（P0）

### 1.1 现象与根因

复审方拿包重算，得到三组互相打架的数字（`ADC12DJ5200SE`）：

| 来源 | `i18n_complete` | `i18n_coverage` |
|---|---|---|
| 包内侧车 `<型号>.i18n.json` | `true` | `1.0` |
| 包内 `manifest.json` | `false` | `0.9837` |
| 根 README | `true` | `1.0` |

根因不是算法错，是**人漏了一步**：同日修订重出包时更新了侧车与 README，
`manifest.json` 停在修订前的值，侧车哈希也没重算。

> 需要说明的一点：这份复审抓的是 `6777f12`（V5 首次推送）的包。
> 同日 `860433c` 已修过一次，仓库 HEAD 上的 V5 清单是 `true / 1.0000`。
> 但**这不能当成反驳** —— 复核方拿到的就是那一份，而且「靠人记得重出」本身就是缺陷。

### 1.2 修法：不是「下次记得」，是机器拦

新增 `qc/bundle_selfcheck.py`，在打包最后一步把清单里**每一个可复算的数值**从包内文件重算一遍：

| 重算项 | 从哪算 |
|---|---|
| 每个成员的 `sha256` / `size` | 分卷目录里的实际文件（PDF 原始字节，文本 CRLF→LF 归一） |
| `i18n_complete` / `i18n_coverage` | 包内 `<型号>.i18n.json` 侧车 |
| `data_anchor` | 包内 `facts_audit.csv` 逐行统计 |
| `pdf_sha256_packaged` / `pdf_hash_match` | 包内 `<型号>.pdf` |
| `artifacts` | `present` 列表长度 |
| ZIP 内每个成员哈希 | 分卷 ZIP（复核方实际下载的那一份） |
| `包校验报告.json` 的 `zip_sha256` | 分卷 ZIP 原始字节 |

任何一项对不上 → `RuntimeError`，**打包直接失败**，不会产出可发布的目录。

它**刻意不复用** `delivery_bundle.py` 的哈希函数，而是自己实现一遍：
共用同一个函数的话，函数写错了自检也会跟着错 —— 那不叫校验，叫复读。

复核方可以自己跑同一份脚本（它就在包里）：

```bash
python qc/bundle_selfcheck.py --out delivery-20261101-V6
```

### 1.3 `包校验报告.json` 的 `i18n_validation` 自相矛盾

V5 报告写 `i18n_validation: not_checked`，而清单里已经有实测覆盖率 —— 复审一眼看出矛盾。
根因是**两件事被塞进了一个字段**。V6 拆开：

| 字段 | 谁给结论 | 取值 |
|---|---|---|
| `i18n_coverage` | 机器（渲染层侧车） | `measured` / `not_checked` |
| `i18n_content_review` | 人工语言审校 | `not_reviewed`（本管线不做） |

**覆盖率不等于译文质量**：`ratio=1.0` 只说明「没有回退到英文」，不说明「译得对」。
语言审校是独立工序，不能由这个字段代签。

### 1.4 `pin_desc_exempt` 由空串改为布尔

V5 三件板卡件该列是 `""`，读者分不清「不适用」与「没算」。
V6 起恒为 `true` / `false`。实测：`true, true, false, false, false`。

## 二、唯一状态推导机（P0）

### 2.1 现象

`facts_audit.csv` 里同样的字段特征给出了不同结论：74 行带 `row_sha256` 却不是
`verified_row`，14 行带 `bbox` 却停在 `value_on_label_page`。
复审原话：「这会让客户觉得你们的审计系统是『人工手填』的」。

### 2.2 两个真实根因

1. **判定顺序不单调**：容器级复现（`verified`，无坐标）排在「审计器自己找到行」
   （`verified_value`，有坐标）之前，能拿到坐标的行被降级成无坐标。
2. **输出字段取自 JSON 自述**：`row_sha256` / `bbox` 一开始就从 JSON 抄下来，
   弱证据分支忘了清空 —— 于是出现「带指纹却只到同页」。
3. 附带一个数值判据过严：重放行常比 JSON 多印 typ 或脚注标号
   （`VA19 1.8 / 1.9 / 2.0` 对 JSON 的 `1.8 to 2.0`），`==` 判据把这些行全判成不匹配。

### 2.3 修法

`audit_one()` 里不再写 if/elif 链，改成三步：

```
证据收集（只收能从 PDF 重算的）  →  _derive() 唯一推导  →  _emit_fields() 按结论发字段
```

* **`_derive()`**：一条严格单调的阶梯，从上往下第一个成立的就是结论；
  循环里不许再写第二个 if 去改判。
* **`_emit_fields()`**：结论 → 字段白名单。`verified_row` 之外的行，`row_sha256` 一定是空串。
* **`_check_consistency()`**：逐行核「字段 ↔ 结论」，违反则**拒绝写出报告**（退出码 3）。

于是有了一条可机器验证的不变式：

> `row_sha256` 非空 ⟺ `verified_row`；`bbox` 非空 ⟺ 坐标级结论。

V6 实测：**0 行**违反。

### 2.4 新增 `verified_paragraph`（正文条目级）

表格之外的参数（Features 条目、板卡规格正文、点线排版的绝对最大额定值）
拿不到表格行指纹，但能拿到**坐标 + 条目指纹**：

* `page` + `bbox`（PDF 文本行的真实坐标）；
* `paragraph_sha256 = sha256(page | 归一化行文本)` —— 复核方拿同一页同一行就能重算。

四条精度闸，宁可锚不上也不猜：

1. 这一行必须包含该行声明的**每一个**数值；
2. 同页含全部数值的行 > 3 条时，**必须**靠标签里有辨识度的词定位
   （没有这条，`Analog Input: Voltage` 会锚到 `Digital Input Voltage to DGND` 上 ——
   两个通用词碰巧对上，但那是**完全不同**的参数，实测踩到）；
3. 名字覆盖度 ≥ 0.6，或条件串覆盖度 ≥ 0.6（板卡正文几乎只靠条件定位）；
4. **唯一最优**：并列就返回 None。排序末位还比「这一行比本行多印了几个数」与窗口长度。

「主条目 + 缩进子条目」在 PDF 里是两行，单行接不上（ADC 的
`Noiseless Aperture Delay Step` 就是），因此另有 2~3 行的**连读窗口**兜底，
且**单行优先**：能锚一行就不锚两行。

### 2.5 效果

| 型号 | V5 `data_anchor` | **V6** | 说明 |
|---|---|---|---|
| `ADC12DJ5200SE` | 88/108 | **108/108** | 20 条「同页」清零 |
| `ADS1201U-1/1K` | 31/50 | **46/50** | 剩 2 条同页 + 2 条无数值 |
| `ADS8568EVM-PDK` | 14/14 | **14/14** | 无回退 |
| `BOOST-DRV8711` | 0/2 | **2/2** | 正文段落锚定 |
| `BOOSTXL-C2KLED` | 0/5 | **5/5** | 正文段落锚定 |

风险队列：**61 行 → 19 行**（`human_review` 44 → 2）。

## 三、页面 `†` 改由事实表驱动（P1）

### 3.1 现象

复审 新-3：JSON 标 `audited_row_anchored` 的 4 行（`ENOB` / `Supply Voltage - VA19/VA11/VD11`），
事实表判 `value_on_label_page`。页面 `†` 跟 JSON 走，于是**同一个包里「哪些行已核验」有两种答案**。

### 3.2 修法

`qc/fact_acceptance.py` 落盘 `<验收根>/facts_verdicts.json`（`label ␟ 条件 → verdict`），
渲染层把它挂到 `doc.metadata.facts_verdicts`，`_is_unverified()` **有它就只按它判**，
不再看 `verification.status`。键里带条件串是因为 AC 表同一个 `parameter`
会因测试条件不同出现十几条（ADC 的 SFDR 有 10 条），只按 label 查会让
「一条弱证据」把同名的十条全打成 †（实测踩到）。

装配顺序因此变成两趟：装配 → 事实表 → 再装配（`--keep-out` 原地重渲染）。

### 3.3 关于那 4 行：**没有降级，是事实表升级了**

复审建议「以更严的 `facts_audit` 为准，把这 4 行降为 `value_on_label_page`」。
我们按同一原则复核后发现方向相反：这 4 行**确实能从 PDF 重放出行指纹**
（`VA19, analog 1.9-V supply  1.8 1.9 2.0` / `AIN = -1 dBFS  7.88 8.5`），
V5 之所以判「只到同页」，是因为旧代码用数值**全等**比对，而重放行多印了 typ 列。

修好判据后事实表给的是 `verified_row`，比 JSON 原先的自述**更强**，
所以最终动作是「事实表升级 + 页面跟事实表」，而不是降级。两处口径现在一致。

### 3.4 页面 `†` 实测

| 型号 | 行内 `†` | 与事实表弱证据行数 |
|---|---|---|
| `ADC12DJ5200SE` | **0** | 0 |
| `ADS1201U-1/1K` | **4** | 2 同页 + 2 无数值 |
| `ADS8568EVM-PDK` | **0** | 0 |
| `BOOST-DRV8711` | **0** | 0 |
| `BOOSTXL-C2KLED` | **0** | 0 |

（AC 表此前完全没有 `†` 支持，V6 补上：角标打在 SYMBOL 格。）

## 五、amax 列角色推广到 ADS1201U（P1）

复审 新-5：ADS1201U 的 11 条 `absolute_max` 仍是 7 `unresolved` + 4 `model_unverified`。

根因不是没调 `fill_absolute_max()`，是**它看不见这张表**：
ADS1201U 的绝对最大额定值表是「参数名 + 点线 + 值」排版，
`find_tables()` 整页只识别出一个 2 行的小表，`extract_spec_rows()` 取面积最大的表 ——
于是 11 条一条也匹配不上。

V6 两处改动：

1. **同页多表全部试一遍**，按「能匹配最多条」选表，而不是按面积选（面积与
   「是不是绝对最大额定值表」没有关系）。
2. 新增**点线行抽取**（`_amax_dot_rows`），只解析无歧义的形态：
   `–0.3V to 6V`（MIN/MAX 由 `to` 这个词决定，不是猜列）与单值（只能是上限）。
   `±100, Momentary; ±10, Continuous` 这类复合值**不解析** —— 拆错等于伪造。

结果：**4 条 `audited_deterministic` + 5 条 `audited_paragraph`**（符号值逐字核对，
主张「原文这一行印的就是这个值」，不主张列角色），剩 1 `model_unverified` + 1 `unresolved`。
**值一个字都没改**（`replaced=0`）。

> 期间踩到一个真坑：放宽到「命中一个编号词」时，`REFIN Voltage to AGND` 与
> `AVDD to AGND` 都含 `AGND`，0.5 分就把前者认到后者那行，`-0.3V to AVDD +0.3V`
> 被改写成 `-0.3 to 6` —— **伪造**。现在要求点线行至少撞上两个编号词。

ADC 的 15/15 列角色回验**无回退**（回归测试锁死）。

> 所以最终按「值形态对齐原文」补了，做法见 §八。

## 八、可复现

```bash
# 1) 装配（口径归一）
python qc/stage_release.py --src data/staging_20261101_v5/parsed \
  --out data/staging_20261101_v6 --alts-from data/staging_20261101_v5/alts \
  --langs ja,ko,de,es --normalize --force

# 2) 逐行回打 PDF（产出 facts_audit.* + facts_verdicts.json）
python qc/fact_acceptance.py --staging data/staging_20261101_v6 --pdf-dir data/pdfs

# 2.5) 值形态对齐原文（`2 to 6.3` → `2.0 to 6.3`，数值不变）
#      qc/postprocess_qwen.py::align_decimal_form，按行 bbox 取原文小数写法。
#      必须在装配之后、重渲染之前 —— 它改的是 parsed JSON，页面从 JSON 来。

# 3) 再装配：页面 † 跟事实表走（--keep-out 原地重渲染）
#    src 指向 staging 自己的 parsed（此时已含对齐后的值）；
#    --pdf-dir 用生产源，**不要指 staging/pdfs** —— 那是复制目标，copy2 会撞 WinError 32。
python qc/stage_release.py --src data/staging_20261101_v6/parsed \
  --out data/staging_20261101_v6 --keep-out \
  --pdf-dir data/pdfs --langs ja,ko,de,es

# 4) 打包（末尾强制跑自证链自检）
python delivery_bundle.py --acceptance-root data/staging_20261101_v6 \
  --out data/delivery-20261101-V6

# 5) 独立复核（复核方也可跑）
python qc/bundle_selfcheck.py --out data/delivery-20261101-V6
```

### 8.1 值形态对齐的实现要点

`align_decimal_form(entries, pdf)` 只做一件事：区间端点是**整数形态**、
且该行 `bbox` 区域里存在**唯一**一个浮点值相等的带小数点字面量时，把形态换回去。

三条护栏（都有用例）：

1. **数值必须相等** —— 改成 `2.5` 就是编造，不是对齐；
2. **必须有 `page` + `bbox`** —— 全页搜索会把别处的 `2.0` 认过来；
3. **区域里同值写法必须唯一** —— `2.0` 与 `2.00` 同时出现就不动。

另外踩到一个接口坑：`process()` 传进来的是 **PDF 路径**（`resolve_pdf()` 的返回值），
不是已打开的文档。直接下标会抛 `TypeError` 并被 `except` 吞掉 ——
表现是「永远 0 条」的哑弹。`tests/test_decimal_form_align.py` 有一条用例专门锁这个。
