## 1. 为什么先解决采样不稳定（而不是先重解析）

复审报告已明确：客户会用 Codex 复跑我们的产物。上一轮 v4/v5 两次解析的差异是：

| 运行 | electrical | VCMI | pins | ESD |
|---|---|---|---|---|
| v4 | 19 | **全缺** | 64（纯序号） | `+2000` |
| v5 | 23 | 3 条 `0 to 0.55` | 144（球位号） | `±2000` |

同一份 prompt、同一份 PDF、`temperature=0.0`。**这种差异不是"算错"，是"每次复跑都要重新吵一遍"**。
所以 V4 的第一件事不是打包，是把核心字段的产出方式换掉。

### 1.1 分工原则

| 字段 | 数据源 | 为什么 |
|---|---|---|
| `pin_configuration` | 文本层 + 球位正则 + 成组行展开 | `find_tables` 会吃掉描述空格（`Analog supply ground` → `Analogsupplyground`） |
| `specs.thermal` | 文本层 | `find_tables` 融合小数位（`0.23`→`023.`），融合后**无法反推小数点位置** |
| `specs.esd` | 文本层 | 同上；且必须保留 `±` 号 |
| VCMI / VID | 文本层，按引脚族拆条 | p10 ROC 与 p12 EC 是**同名不同表**，模型会合并成一条并留下错的 typ |

### 1.2 可复现性实测：三次独立解析

```
pins      eb2145b82eb596ee  ×3   144 个球位
thermal   4dd75f753101dc12  ×3   5 条（RθJA 23.9 / RθJC(top) 0.8 / RθJB 8.4 / ψJT 0.23 / ψJB 8.4）
esd       a594a1e8e76d13f9  ×3   HBM ±2000 V / CDM ±500 V
vcmi_vid  e9baa1ab6c95c68c  ×3   3 条 VCMI + 1 条 VID
```

三次分别是 `data/_v4run_a`、`data/_v4run_b`、`data/_v4run5`（V4 交付件取自第三次）。
四个指纹全等 —— **不是"这次跑对了"，是"怎么跑都一样"**。

### 1.3 客户怎么自证

不需要装本仓库的工具。每个 `<型号>.json` 自带指纹：

```json
"metadata": {
  "core_sha256": {
    "pins":     {"count": 144, "sha256": "eb2145b8…"},
    "thermal":  {"sha256": "4dd75f75…"},
    "esd":      {"sha256": "a594a1e8…"},
    "vcmi_vid": {"count": 4,   "sha256": "e9baa1ab…"}
  }
}
```

复跑同一份 PDF 后比这四个 sha256 即可。口径与仓库内的闸门工具完全一致
（同一个函数 `qc/deterministic_extract.py::core_digest`），不会出现"我们自证一致、
客户算出来不一致"的互相打架。

仓库内可复跑的闸门：

```bash
python qc/determinism_check.py data/_v4run_a data/_v4run_b
# 核心字段全等 → rc=0；任何一项不等 → rc=1
```

## 2. 四个验收点：JSON 与页面双证据

V3 的四个验收点里，有两个是"JSON 里没有"，还有一个是"JSON 有了但页面看不见"。
这次逐条对照**两侧**。

| # | 验收点 | JSON（V4） | 页面（V4） | V3 |
|---|---|---|---|---|
| 1 | `Input common-mode voltage` 下限 | 3 条，各 `0 to 0.55 V`，按 CLK± / SYSREF± / TMSTP± 拆开 | 页面出现 `0 to 0.55` **3 次** | 合并成 1 条，下限被抬到 `0.3` |
| 2 | `Input voltage p-p differential` | `0.4 to 2.0 VPP-DIFF` | 出现 1 次 | 缺失/被合并 |
| 3 | 热阻 + ESD | thermal 5 条、esd 2 条 | `23.9` / `0.8` / `8.4` / `0.23` / `±2000` / `±500` **全部出现** | JSON 无容器；页面 0 次 |
| 4 | 球位 | 144 个球位号（`A1`/`G11`/`M12`） | 页面唯一球位 token **144** | 144（旧解析遗留）→ 新解析曾掉到 64 |

### 2.1 页面侧是这次新补的一环

V3 复审的 P1-8 说"页面新增热预算提示段，但**无任何热阻数据**"。当时归因为"JSON 里没有"。
V4 前半程把 JSON 修好后发现还有第二半：**渲染层从来没有输出过 `specs.thermal` / `specs.esd`**。

实测（修之前，V4 的 JSON 已经有 5 条热阻）：

```
'23.9': 0    'RθJC(top)': 0    '±2000': 0    '±500': 0    'ψJT': 0
```

修法：`json_to_txt.py` 在 `#specifications` 段内、绝对最大表之后追加两个子表
（"Thermal resistance" / "ESD ratings"，五语标题）。修后：

```
'23.9': 1    '0.8': 1    '8.4': 2    '0.23': 1    '±2000': 1    '±500': 1
```

**JSON 有了页面看不见，和没有一样。** 这条写进说明，是因为它是这一轮最容易再犯的错。

### 2.2 验收点现在是可执行的断言

`qc/deterministic_extract.py::ACCEPTANCE_SPECS` 把四条验收点写成机器判据：

```python
"ADC12DJ5200SE": {
    "pins": 144,
    "thermal": {"RθJA": "23.9", "RθJC(top)": "0.8", "RθJB": "8.4",
                "ψJT": "0.23", "ψJB": "8.4"},
    "esd": {"HBM": "±2000", "CDM": "±500"},
    "vcmi_value": "0 to 0.55", "vcmi_rows": 3,
    "vid_value": "0.4 to 2.0",
}
```

`check_acceptance(doc, mpn)` 逐条比对，不达标进 `metadata.core_validation`。
客户/复审看到"四验收点通过"时，能对上每一条，而不是一句结论。

## 3. 核验状态上页面（Reviewer V3 新-1）

V3 交付件里 17 条电气行**全是未核验态**（9 条 `not_checked` + 5 条 `unresolved` +
3 条 `condition_unverified`），但页面实测这些字样出现 **0 次**。复审的判定是
"内部治理、外部静默"，风险定级为高。

V4 的处置：

- 行尾加 `†`（纯文本，不带标签 —— `table()` 只对以标签开头的整格放行 HTML，
  塞 `<span>` 会被转义成字面量，这是踩过的双层实体事故）；
- 表头上方加提示条"N of M entries below are marked unverified (†)…"，**五语**；
- 判据是黑名单 + 字面兜底：`condition_unverified` / `unresolved` /
  `column_roles_not_verified` / `not_checked` 都上标记，`audited*` 一律不上标记
  （否则代码抽出来的 VCMI 会被自己的标记反咬）；
- **完全没写 `verification` 的行不上标记**：那是"管线没表态"，不是"管线说没核过"。

实测（V3 交付件重渲染）：

```
notes: 2
  - 17 of 17 entries below are marked unverified (†) — …
  - 6 of 6 absolute-maximum entries are marked unverified (†).
daggers: 25
```

V4 包里的真实分布（这就是"门禁在真数据上真的会响"的证据）：

```
BOOST-DRV8711     † × 3    （V3 遗留 JSON 带未核验状态，沿用）
BOOSTXL-C2KLED    † × 6    （同上）
ADC12DJ5200SE     † × 0    （4 条确定性行是 audited_deterministic，其余行未写状态）
ADS1201U-1/1K     † × 0    （同上）
ADS8568EVM-PDK    † × 0    （评估板，无芯片级行）
```

ADC 那 0 个 † 是"没表态不臆断"的口径，不是门禁没生效 ——
同一套渲染在带状态的件上（两件 BOOST）立刻打出 3/6 个角标。
门禁本身另有 18 个用例守着（`tests/test_verify_render_and_digest.py`）。
若要求逐行核验披露，需先跑 `table_audit` 给每行打状态，那是另一件事（见 §5.2）。

## 5. 仍然存在的问题（如实登记）

### 5.1 电气表里模型抽的行仍会漂

核心字段稳了，但**非核心电气行**还是模型写的，两次运行仍有差异。以 `_v4run_a` /
`_v4run_b` 为例：

```
rows a=23 b=22   identical=False   drift=24
  - 15 行行名措辞不同：`Sampling Rate - Single Channel Mode` ↔ `Sampling Rate (Single Channel)`
  - 值真差 2 处：`Power Consumption` A=4.01 W / B=4 W（B 还丢了条件串）
                 `NCOs per DDC` A=Four independent 32-Bit NCOs / B=4 32-Bit
  - 3 处只有 condition 不同（`Supply Voltage - VA19/11/VD11` 的 typical 条件）
```

**这就是"代码抽的确定、模型抽的不确定"的分界线。** 处置路径已经清楚
（继续把结构确定的行搬进 `deterministic_extract`），但这一轮没做完，
不冒充已解决。客户可用 `qc/determinism_check.py` 自己数漂了多少。

### 5.2 逐行核验没有重跑

V4 没有对电气表重跑 `table_audit`。原因：条件同源钳制在融合列上定位不到行
（V3 遗留问题，v5 有 7 条 `condition_unverified`，而条件在 p10 里逐字存在），
重跑会把确定性抽出来的干净 VCMI 三条又标回未核验。**宁可不标，也不覆盖已确认的行。**

## 7. 全量测试为什么从 18 分钟降到 3 分钟

第一次跑全量挂了 **17 分 51 秒**，最后不是失败在用例上，而是 **collection error**：

```
imported module 'test_identity_scope' has this __file__ attribute:
  E:\workspace\IcPdfParser\data\code_backup_scope\test_identity_scope.py
which is not the same as the test file we want to collect:
  E:\workspace\IcPdfParser\tests\test_identity_scope.py
```

根因：仓库根**没有 pytest 配置**，pytest 从根开始递归，把 `data/` 下几万个 JSON、
`.sandbox/` 里的临时脚本、`data/code_backup_scope/` 里的备份模块全扫了一遍 ——
18 分钟里绝大部分花在收集阶段，真正跑用例只要 3 分 18 秒。

修法（`pytest.ini`）：

```ini
testpaths = tests
norecursedirs = .git .sandbox data docs node_modules __pycache__ .workbuddy* .pytest_cache
markers =
    slow: 读真实 PDF 或走完整渲染链，本地可跳过，发版前必跑
```

**刻意不写 `addopts = -m "not slow"`**：把慢用例默认关掉，会让"全绿"变成一句
没人知道前提的结论。

慢用例只有 4 个（`--durations` 实测，合计约 70 秒），都是读真 PDF 的：

| 用例 | 耗时 |
|---|---|
| `test_table_cell_num.py::TestIccRowRealPdf::test_icc_cell6_spans_min_and_max` | 21.9s |
| `test_table_cell_repair.py::TestRepairFromWords::test_iiz_row_numbers_are_recovered` | 20.1s |
| `test_table_cell_repair.py::TestRepairFromWords::test_supply_voltage_decimals_are_recovered` | 19.8s |
| `test_pin_repair.py::test_real_pdf_all_144_source_rows_mapping_and_coverage` | 10.3s setup + 8.7s |

日常迭代 `pytest -m "not slow"`（实测 1195 passed / 1 skipped，119.9s），发版前跑 `pytest` 全量（1199 passed，198.4s）。

顺带确认了两件容易怀疑但**不是**性能问题的：

- **没有 ReDoS**：`deterministic_extract.py` 里 4 个正则（`BALL_RE` / `NUM_RE` /
  `FOOTER_RE` / `FAM_RE`）都是线性模式，没有嵌套量词；
- **没有 PDF 句柄泄漏**：`pymupdf.open()` 全部包在 `try/finally: close()` 里。
