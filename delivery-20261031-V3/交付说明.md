## 三、页面片段与 SEO 侧车（交付契约，必读）

本包的 HTML **是内容片段，不是整页**：每个 `.html` 以 `<div class="pd-wrap">` 开头，
**不含** `<html>` / `<head>` / `<title>` / `<meta name="description">` /
`<link rel="canonical">` / `hreflang` / JSON-LD。这是契约，不是缺漏。

因此：

- 标题、meta description、keywords、多语标题在 **`<型号>.seo.json` 的 `page` 节点**（侧车）；
- 多语叙述段在 `<型号>.ja.html` / `.ko.html` / `.de.html` / `.es.html` 片段内；
- 片段里的 `<h1>` 已使用 `seo.json` 对应语种标题（注入管线只接到 h1，未接 head）；
- **复核时请勿**把「片段没有 `<title>` / 没看到 meta」判为缺陷，应判「框架是否注入」；
- 若需求方要求整页交付，须先改本契约并同步渲染层，不能靠片段自带头部。

## 六、校验边界与哈希口径

包校验只覆盖：allowlist 恰好 5 件、ZIP 成员正斜杠且无路径穿越、无重复成员、逐成员 CRC、
源文件 / 独立目录 / ZIP 成员三处 SHA-256 一致；最终 ZIP 哈希单独存于 ZIP 外的
`包校验报告.json`，避免循环哈希。**打包层不校验参数正确性、对象归属与本地化。**

**哈希口径：`sha256` 按 CRLF→LF 归一化后计算**，与平台无关；报告 `hash_rule` 字段显式记录。
若直接对原始字节算哈希，Windows 写出的 CRLF 与 git clone 得到的 LF 会得出不同值
（实测同一文件 `752afff8…` 与 `df10bcd6…`），那不是数据被改，是换行符差异。
