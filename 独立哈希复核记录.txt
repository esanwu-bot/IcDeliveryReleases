五、关于「最终提交 SHA」—— 为什么本文件里没有它
----------------------------------------------------------------
git 的提交号 = sha1( tree + parent + author + message )，而 tree 里含
本文件的 blob 哈希。让一个文件写出「包含它自身的那个提交」的哈希，等于
求解一个固定点：改文件→改 blob→改 tree→改提交号→文件又要改。这不是
工程上麻烦，是在数学上不成立。任何声称做到了的，那个值一定是伪造的。

所以这一环改由**提交消息**承担（提交消息不参与自身的自指困境）：
  提交消息  → 声明本文件的 SHA-256 与本 ZIP 的 SHA-256
  本文件    → 声明本 ZIP 的 SHA-256 与两个成员的 raw SHA-256
  ZIP       → 成员原始字节

提交 SHA 由复核方当场用 git 打印（见下一节第 1 条），并与
  git ls-tree <提交> -- "独立哈希复核记录.txt"
给出的 blob 哈希交叉验证：能同时对上，就证明「这份记录确实属于那个提交」，
这比文件自己写一个提交号强得多 —— 自写的号码无从证伪。

六、复核方验证命令（五条，全部通过即闭链）
----------------------------------------------------------------
  # 1) 取到提交号与提交消息（消息里应有两个 sha256）
  git log -1 --format='%H%n%B'

  # 2) 本文件的 blob 哈希必须与 1) 中 git ls-tree 的结果一致
  git ls-tree HEAD -- "独立哈希复核记录.txt"

  # 3) ZIP 的 SHA-256 必须同时等于：本节 1) 消息里的值、
  #    本记录第一节的值、《包校验报告.json》的 zip_sha256
  sha256sum delivery-batch20-eval-V3-RELEASE-V3.1/part-0001-of-0001.zip
  python -c "import json;print(json.load(open('delivery-batch20-eval-V3-RELEASE-V3.1/包校验报告.json'))['zip_sha256'])"

  # 4) 两个成员的 raw SHA-256 必须等于本记录第二节的值
  unzip -o -q delivery-batch20-eval-V3-RELEASE-V3.1/part-0001-of-0001.zip -d /tmp/x && sha256sum /tmp/x/facts_audit.json /tmp/x/risk_queue.csv

  # 5) 包内自检结果：直接读报告，不需要本项目的源码
