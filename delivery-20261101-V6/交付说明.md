# 交付说明（delivery-20261101-V6）

> 与 `delivery-20261101-V5` 的差异集中在**五件事**：
> ① **打包自证链闭环** —— 清单里每个 `sha256` 与每项指标，打包末尾都拿包内文件重算，
> 对不上直接中断出包（不再是「下次记得同步」）；
> ② **唯一状态推导机** —— 一行的证据等级只能由一个函数推导，页面 `†` 改由事实表驱动，
> 不再出现「JSON 说 A、事实表说 B」；
> ③ 新增 `verified_paragraph`（段落级坐标证据），把「两行主条目 + 缩进子条目」这类
> 排版接上；`data_anchor` 从 **88/108 → 108/108**；
> ④ `absolute_max` 的**点线排版**（`名称……值`）改走确定性抽取，ADS1201U 的 11 行不再靠模型；
> ⑤ 板卡页 `ADS8568EVM-PDK` 的 Thermal / ESD / AC 三段各加一句**归属声明**。

## 这是什么

五型号（ADC12DJ5200SE / ADS1201U-1/1K / ADS8568EVM-PDK / BOOST-DRV8711 / BOOSTXL-C2KLED）
的详情页物料与解析 JSON 交付包，**复核候选版**，不是已批准上线的正式版本。

- `release_status` 全部 `not_approved`
- `release_state` 实测：ADC / 两件 BOOST **`IDENTITY_APPROVED`**、
  ADS8568EVM-PDK **`DATA_VALIDATED`**、ADS1201U-1/1K **`PACKAGING_PASSED`**（`46/50`）
- `CONTENT_APPROVED` / `RELEASE_APPROVED` 未申请，需人工签核
- `i18n_complete` / `i18n_coverage` 为**实测值**，且**打包时从侧车重算**

**打包校验通过不等于工程验收通过，不应直接上线或用于电路设计。**

> **本包已包含全部原厂 PDF 原件**（五件，`<型号>/<型号>.pdf`），
> 复核方可对照包内 PDF 逐行复核任意一条参数，不需要外部下载、也不需要相信清单里的哈希。

## 怎么用这个包核对

1. 打开 `manifest.csv`，看每件的 `gate` / `release_state` / `facts_verdict` / **`data_anchor`**。
   `data_anchor` 写「已锚定/总行数」—— 分子小于分母就说明有行只到「同页」，
   缺口在这里直接可见，不再藏在 `pass` 里。
2. 打开 `facts_audit.csv`，这是**逐行**的 PDF 回打结果，九级结论：

   | 结论 | 含义 | 随附字段 |
   |---|---|---|
   | `verified_row` | 锚到原厂表的具体**行** | `page` + `bbox` + `row_sha256` |
   | `verified_paragraph` | 锚到具体**段落**（排版是「主条目 + 缩进子条目」两行时） | `page` + `bbox` + `paragraph_sha256` |
   | `verified_value` | 值有坐标，但行归属未定 | `page` + `bbox` |
   | `verified` | 确定性抽取器逐字复现（容器级，无行坐标） | — |
   | `value_on_label_page` | 值与参数名同页，行/列未证 | — |
   | `value_in_pdf` | 只在别处出现，归属未证 | — |
   | `partial` / `unchecked` / `not_found` | 未达上述任何一级 | — |

   **不变式**（代码里有断言，`qc/fact_acceptance.py::_check_consistency`）：
   `row_sha256` 非空 ⟺ `verified_row`；`bbox` 非空 ⟺ 坐标级结论。
   看到「有哈希却不是行级」或「有坐标却是弱结论」即为缺陷，请直接报。
3. 需要怀疑某一行时，直接打开该型号目录下的 `<型号>.pdf`，
   按 `facts_audit.csv` 里给的页码与 `bbox` 翻过去对照。**包内 PDF 就是解析用的那一份**，
   `pdf_sha256_packaged` 可与 `pdf_sha256_recorded` 独立比对。
4. `risk_queue.csv` 是待处理清单，每行带 `suggested_action`
   （`human_review` 需人工看图确认 / `promote_to_deterministic` 可转确定性抽取）。
   V6 起 **61 行 → 19 行**，其中 `human_review` 从 44 行降到 **2 行**。
5. `txt/<型号>.i18n.json` 是多语覆盖率侧车：每语种的 `keys_used` / `key_fallbacks` /
   `narrative_fallbacks` / `ratio` 都在里面。**清单里的 `i18n_coverage` 就是从这里取的**，
   取所有语言里最低的那个。

## 自证链：清单里的每个数都能重算

V5 被判「自证链断裂」的真实经过：侧车说 `i18n_coverage = 1.0`，清单停在修订前的
`0.9837`，侧车文件的 `sha256` 也没重算。复核方拿包一算，两边都不符 ——
**不是数据错了，是自证链断了**，于是「我们实测过」这句话在这个包里失去证明力。

V6 的修法不是「下次记得」，而是打包末尾跑一遍独立实现的自检
（`qc/bundle_selfcheck.py`，**刻意不复用打包器的哈希函数** —— 共用则函数错了自检也跟着错）：

| 重算项 | 依据 |
|---|---|
| 每个成员的 `sha256` / `size` | 包内文件（文本按 CRLF→LF 归一，PDF/ZIP 按原始字节） |
| `i18n_complete` / `i18n_coverage` | 侧车 `<型号>.i18n.json`（取所有语言里**最低**的覆盖率） |
| `data_anchor` | 随包 `facts_audit.csv` 逐行数 |
| `pdf_sha256_packaged` / `pdf_hash_match` | 包内 PDF 原始字节 |
| `artifacts` | 记录里的 `present` 计数 |
| ZIP 内成员哈希 / 非法路径 | 分卷 ZIP 本身（复核方拿到的就是这一份） |
| 报告里的 `zip_sha256` / `verified_members` | ZIP 实算 |

**任一项对不上，打包直接中断并报错**，不会产出一个「看起来完整」的包。
清单里 `包校验报告.json → self_check: "pass"` 即表示这一层已通过。

复核方可自己跑同一套检查：

```bash
python qc/bundle_selfcheck.py --out <解压后的包根目录>
# 通过 → 退出码 0；不一致 → 逐项打印差异，退出码 1
```

## 页面上的 `†` 是怎么来的

V5 及以前，页面 `†`（未核验标记）读的是 **JSON 自己的 `verification.status`**，
而 `facts_audit.csv` 是另一套独立推导 —— 两边各说各话时，页面会替 JSON 撒谎。

V6 起 `†` 由 `facts_verdicts.json` **统一驱动**，键是 `label ␟ 条件`
（AC 表同一个 parameter 有 10 条，只按 label 打会把一条弱证据扩散成十次）。
页面结论不会强于事实表：事实表说 `verified_row` 的，页面不打 `†`；
事实表说 `value_on_label_page` 的，页面打 `†` 并允许悬浮查看。

## `release_state` 的升降说明（为什么不是五件都到顶）

`release_state` 是五级阶梯，**前三级自动、后两级只认 `signoff.json`**：

```
PACKAGING_PASSED → DATA_VALIDATED → IDENTITY_APPROVED → CONTENT_APPROVED → RELEASE_APPROVED
```

- `PACKAGING_PASSED`：四件必带物料齐备，且随包 PDF 与 `pdf_hash` 一致。
- `DATA_VALIDATED`：`core_validation=pass`、事实验收表无 MISMATCH，
  **且每一行有数值的工程参数都锚到原厂表的具体行/段落**（`data_anchor` 分子 = 分母）。
- `IDENTITY_APPROVED`：身份状态已审核（`IDENTITY_SUPPORTED` / `BOARD_CONFIRMED`）。
- `CONTENT_APPROVED` / `RELEASE_APPROVED`：**需要人工签核**，代码不代签。

本包实测：

| 型号 | `data_anchor` | `release_state` | 卡在哪 |
|---|---|---|---|
| `ADC12DJ5200SE` | 108/108 | `IDENTITY_APPROVED` | 后两级需签核 |
| `BOOST-DRV8711` | 2/2 | `IDENTITY_APPROVED` | 后两级需签核 |
| `BOOSTXL-C2KLED` | 5/5 | `IDENTITY_APPROVED` | 后两级需签核 |
| `ADS8568EVM-PDK` | 14/14 | `DATA_VALIDATED` | `identity_state` 未达审核态 |
| `ADS1201U-1/1K` | 46/50 | `PACKAGING_PASSED` | 4 行未锚到具体行 |

**关于「V5 起主力件降级」的说明**：V5 把 `DATA_VALIDATED` 的门槛从
「`verdict=pass` 就放行」改成「每一行都要锚到具体行」，因此当时 4/5 掉到
`PACKAGING_PASSED` —— 那是**审计口径变严，不是数据变差**。
V6 把锚定率补上去之后，主力件回到了 `IDENTITY_APPROVED`，比 V4 的口径更严、级别更高。

**`ADS1201U-1/1K` 停在 `PACKAGING_PASSED` 是刻意留的缺口**：`46/50` 里有 2 行
只有「值与该参数名同页」、2 行没有可回打的数值。不把它们算成「已锚定」，
缺口就摆在 `data_anchor` 这一列上，复核方一眼能看到差在哪。

所以本包即使 `data_anchor` 全满，**也不会自动升到 `CONTENT_APPROVED`** ——
这不是漏了一步，是设计：机器能证明「值出自哪里」，不能替人决定「这个值能不能上页面」。

## 板卡页的参数归属

`ADS8568EVM-PDK` 挂的 PDF 是 **ADS8568 的器件手册（SBAS543C）**，
整板的电源/连接器规格根本不在那份文件里 —— 所以它全部归 `onboard_device`。

V6 起，Thermal / ESD / AC 三段**各自**在段首印一句：

> These values are specified for the on-board ADS8568 device; they are not limits
> for the assembled board.

**不假装有整板参数。** 声明必须逐段印，不能只在页顶印一次 ——
读者是跳着看的，看到 RθJA 那一行时未必刚读过页首。

`BOOST-DRV8711` 的用户指南里同时有两类参数，按行打 `attribution`，页面上分成
`Board-level parameters` / `On-board device parameters` / `Attribution not determined`
三张表（单桶时不印标题，芯片页不受影响）：

```
Voltage Range                    8.2 to 52 V    External power supply input   ← 整板
Continuous Current per H-Bridge  4.5 A          Max continuous                ← 板载 DRV8711
```

## 多语覆盖率 vs 多语内容审校（两个字段，别混）

| 字段 | 含义 | V6 取值 |
|---|---|---|
| `i18n_coverage` | **机器实测**：目标语言里有多少 key 有译文、多少回退到英文 | 三件 `1.0000`（ADC / ADS1201U / ADS8568EVM）；两件 BOOST 板卡 `0.9661` / `0.9623` |
| `i18n_content_review` | **人工审校**：译文读起来对不对、术语是否统一 | 全部 `not_reviewed` |

V5 把这两件事塞进同一个 `i18n_validation` 字段，于是「覆盖率 1.0」被读成
「多语已验收」。V6 拆开：**覆盖率 1.0 只证明「没有回退到英文」，不证明译文质量。**

另：`pin_desc_exempt` 现在是**布尔字符串** `"true"` / `"false"`（V5 有空串），
清单里不会再出现第三种形态。

## 管脚描述为什么保留英文

`pin_configuration` 的描述是管脚功能名（`VDD` / `AGND` / `SDO/SDI` / `No connect`）。
IEEE 器件手册与封装规格里这类文字按英文原样引用，译成目标语言反而与读者手上的
datasheet 对不上 —— 这是工程惯例，不是漏翻。

清单中 `pin_desc_exempt="true"` 表示该型号适用此豁免，页面上有一行小字说明。
**豁免仅限 `pin_configuration`**；features / applications / description /
technical insight / FAQ 不豁免，仍按实测覆盖率考核。
